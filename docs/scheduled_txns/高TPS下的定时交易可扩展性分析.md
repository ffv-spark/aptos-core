# 高 TPS 场景下的定时交易可扩展性分析

## 前提假设

让我们抛开 "每区块100条" 的限制，按照 Aptos 的实际能力来分析。

### Aptos 的性能参数

```
官方数据：
- 理论最高 TPS: 160,000+ (实验室环境)
- 实际主网 TPS: ~10,000 (当前)
- 预期优化后: 30,000 - 50,000 TPS

我们按最乐观的情况分析：
假设 Aptos 能稳定达到 50,000 TPS
```

## 1. 重新计算：10万用户场景

### 场景设定

```
DeFi 协议每日分发：
- 用户数: 100,000
- 调度时间: 每天 00:00 UTC
- 全部用户设置定时交易自动领取
```

### 执行时间计算（高 TPS）

```
假设 Aptos TPS = 50,000

如果定时交易没有限制:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

100,000 ÷ 50,000 TPS = 2 秒

实际考虑:
- 定时交易通常比普通交易复杂 2-3 倍
- 假设定时交易有效 TPS = 20,000
- 执行时间 = 100,000 ÷ 20,000 = 5 秒

看起来可以接受！
```

### 但是... 实际问题

```

### 2.2 数据结构性能退化

```
BigOrderedMap 的性能：

当前实现：B+ 树
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

性能特征：
- 查找: O(log n)
- 插入: O(log n)
- 范围查询: O(log n + k)

100万条记录：
log₂(1,000,000) ≈ 20

每次操作需要：
- 20 次节点访问
- 20 次存储读取
- Gas 成本: 20 × 300 = 6,000 gas

影响：
┌────────────────────────────────────────┐
│ 操作         │ 100条   │ 1万条 │ 100万条 │
│──────────────┼─────────┼───────┼─────────│
│ 插入 (gas)   │ 2,100   │ 4,200 │ 6,000   │
│ 查询 (gas)   │ 2,100   │ 4,200 │ 6,000   │
│ 删除 (gas)   │ 2,100   │ 4,200 │ 6,000   │
└────────────────────────────────────────┘

结论：
- 数据量越大，每次操作越贵
- 用户成本不断上升
- 即使 TPS 很高，单笔成本也高
```

## 3. 经济模型问题（与 TPS 无关）

```
用户视角：

Alice 想在 1 个月后执行转账：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

- 锁定押金: 1000 gas × 100 gwei = 100,000 gwei
- 预期执行成本: 300 gas × 100 gwei = 30,000 gwei
- 超额锁定: 70,000 gwei

执行时（Day 30）：
- 实际 Gas 价格: 50 gwei (网络不拥堵)
- 实际成本: 300 gas × 50 gwei = 15,000 gwei
- 退款: 85,000 gwei

Alice 的机会成本：
- 30 天锁定 100,000 gwei
- 如果用于 DeFi 质押，APY 10%
- 损失: 100,000 × 10% × (30/365) ≈ 822 gwei

实际收益：
- 退款 85,000 - 损失 822 = 84,178 gwei
- vs 直接执行成本 15,000 gwei
- 多花: 5.6倍

用户不会用！
```

## 5. 数学模型：临界点分析

### 5.1 可持续性分析

```
设：
- TPS = T
- 定时交易占比 = R
- 平均执行时间 = E
- 新增速率 = A (每秒)
- 执行速率 = T × R / E

可持续条件：
执行速率 >= 新增速率
T × R / E >= A

临界点：
A_max = T × R / E

示例计算：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
假设：
- TPS = 50,000
- R = 20% (分配给定时交易)
- E = 2 (定时交易比普通交易慢2倍)

最大新增速率：
A_max = 50,000 × 0.2 / 2 = 5,000 个/秒

每天最多：
5,000 × 86,400 = 432,000,000 个

看起来很多？但考虑：
1. 用户重复使用（每天都调度）
2. 实际上是 432M / 每用户调度次数
3. 如果每用户每天调度 10 次 = 43M 用户
4. 如果每用户每天调度 100 次 = 4.3M 用户

但实际上：
- R 不可能一直是 20%（峰值会更高）
- E 可能 > 2（复杂交易）
- 还有取消、过期等操作

实际可持续用户数可能只有 1-2M
```

## 6. 现实世界的限制

### 6.1 峰值处理能力

```
即使 TPS = 50,000，峰值仍是问题：

真实数据（假设）：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
某 DeFi 协议空投：
- 符合条件用户: 500,000
- 领取时间: 1 小时窗口
- 平均分布 (理想): 500,000 / 3600 = 139 TPS

但实际分布：
- 前 5 分钟: 50% 用户领取 = 250,000
  需要 TPS: 250,000 / 300 = 833 TPS
  ✓ 可以处理

但如果是定时交易：
- 全部用户都设置在开始的第 1 秒
- 需要 TPS: 500,000 / 1 = 500,000 TPS
  ✗ 超出能力 10 倍

结果：
- 需要 10 秒处理完
- 后面的用户延迟 9 秒
- 可能错过机会（先到先得）
```

### 6.2 网络传播延迟

```
区块链的物理限制：

即使 TPS 无限，数据传播需要时间：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Aptos 共识（假设）：
- 节点数: 100+
- 分布: 全球
- 延迟: 100-500ms

影响：
1. 状态更新需要时间传播
2. 不同节点看到的"当前时间"不同
3. 可能导致重复执行或遗漏

定时交易的问题：
- 需要全局一致的时间
- 但共识本身需要时间
- 矛盾！
```

### 6.3 用户体验问题

```
UX 问题（技术无法解决）：

问题：用户如何知道交易何时执行？
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

链上方案：

- 或者 00:00:10（队列堆积）

Keeper 方案：
- 设置在 00:00 执行

- 可预测性高

用户更倾向于哪个？
```

## 7. 结论

### 即使 TPS 很高，链上定时调度仍有根本性问题

```
技术问题：
✗ 存储爆炸（与 TPS 无关）
✗ 状态膨胀（与 TPS 无关）
✗ 峰值处理（TPS 再高也有峰值）
✗ 数据结构性能退化（与 TPS 无关）

经济问题：
✗ 押金锁定（与 TPS 无关）
✗ Gas 价格波动（与 TPS 无关）
✗ MEV 攻击（与 TPS 无关）
✗ 成本高（与 TPS 无关）

设计问题：
✗ 时间源不精确（与 TPS 无关）
✗ 执行顺序不公平（与 TPS 无关）
✗ 状态依赖（与 TPS 无关）
✗ UX 差（与 TPS 无关）
```

### TPS 高只能部分缓解执行问题

```
TPS 从 100 → 50,000 的改进：

改善的：
✓ 执行延迟（从分钟级到秒级）
✓ 吞吐量（可以处理更多交易）

未改善的：
✗ 存储成本
